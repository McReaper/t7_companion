# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`t7kb` is the shipped, **agent-first query tool** for a Black Ops 3 modding knowledge base: a single **pure-Go, no-cgo** binary that serves hybrid retrieval (FTS5 BM25 + vector cosine, fused with RRF) over a local SQLite index, `t7kb.db`. The primary surface is an **MCP server** for AI agents; it also has a small CLI. Everything runs locally and offline.

This repo is the **consumer**. It does NOT build `t7kb.db` — that is produced by the sibling **t7_knowledge** repo (see "Two-repo split").

## Repo layout

The repo is three things in one: the **Go tool**, a **Claude Code plugin**, and **install/docs**.

- `cmd/` + `internal/` — the Go tool (`t7kb`): CLI + MCP server. The only compiled artifact.
- `install/install.sh` + `install.ps1` — the **single source of truth for installation**. Everything else that mentions install just invokes these.
- `.claude-plugin/marketplace.json` — the **marketplace** catalog (what makes `/plugin marketplace add McReaper/t7_companion` work). Lists the plugin below as a `git-subdir` source over https: a relative `./plugin` makes `/plugin` treat the install as local and refuse to update it, and the `owner/repo` shorthand clones over SSH.
- `plugin/.claude-plugin/plugin.json` — the **plugin** manifest itself. Marketplace = the catalog, plugin = the thing in it; two files on purpose.
- `plugin/hooks/` — a `SessionStart` hook warns when the t7kb binary's and plugin's versions differ (they update separately). Keep it offline (one `t7kb --version`) and POSIX `sh` (Git Bash on Windows).
- `plugin/skills/*/SKILL.md` — the plugin's skills. `setup` is the **agent's** install action (it runs `install/install.sh` + `claude mcp add`), the agent-facing mirror of the README's install. Each skill's frontmatter `name` equals its directory name (Agent Skills spec; Claude Code lists/invokes plugin skills as `t7kb:<directory>`), and skills refer to each other by that form, `t7kb:<name>`. `plugin/skills/contribute/scripts/check_skills.py` enforces this and the other format rules; `.github/workflows/skills.yml` runs it on every PR, and `plugin/evals/` holds the `claude plugin eval` trigger cases. `contribute` is the authoring guide for the skills themselves (new skill vs extending one, description/trigger craft, claim-shaped headings, grounding order, the follow-ups below) and the path for plugin users to send a fix upstream as a PR — **load it before writing or revising any `SKILL.md`**, and update it when a convention here changes. **Adding, renaming, or removing a skill has two required follow-ups:** update `t7kb:knowledge-base`'s frontmatter `description` (it names every other domain skill to route around trigger overlap — the validator checks it) and `.claude-plugin/marketplace.json`'s plugin description. The README's mermaid diagram deliberately does not enumerate skill names — don't add a hardcoded skill list there.
- `templates/AGENTS.md` — the vendor-neutral primer a user drops at their **BO3 mod-tools root** (not per-map; ancestor-aware tools pick it up from any `usermaps/`/`mods/` subfolder). `setup`'s step 3 offers to fetch it there, plus a `CLAUDE.md` that does `@AGENTS.md` for Claude Code, and `templates/bo3.gitignore`/`.gitattributes` to git-track that root.
- `README.md` — the lean **human-facing** front door: what it is, install, one line per capability, the CLI.
- `docs/clients.md` — per-client MCP config (Codex/OpenCode/Cursor/Copilot/Claude) + the AGENTS.md editor table; lives only here.
- `.claude/CLAUDE.md` (this file) / `docs/NOTICE.md` / `docs/data-model.md` — contributor + licensing + schema docs.

**Ground-truth discovery is closed-loop.** `t7kb:knowledge-base`'s "verify against ground truth" section tells the agent to check the raw mod-tools install; `setup` step 3 already walks up to that root to place `AGENTS.md`/`CLAUDE.md`, so it appends a "Raw mod-tools root: `<path>`" fact to the fetched `AGENTS.md` there, and `t7kb:knowledge-base` checks that fact before searching. Keep this cross-reference intact in both skills.

## Commands

Targets **Go 1.25** (`go.mod`). `GOTOOLCHAIN=auto` (the default) fetches the right toolchain on first build.

- Build: `go build -o t7kb.exe ./cmd/t7kb`
- Cross-compile (what CI ships): `CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./cmd/t7kb`
- Vet: `go vet ./...`
- Lint: `gofmt -l cmd internal` (must print nothing) and `golangci-lint run ./...` (v2.14; `.golangci.yml`). Beyond the standard set it enforces: cyclomatic ≤ 20, cognitive ≤ 30, a function ≤ 80 lines / 60 statements, a file ≤ 500 code lines, and nestif. Tests are exempt from the size/complexity limits. When a function trips one, split it by what it does (one check, one stage, one subcommand) rather than raising the limit or adding a `//nolint`.
- Test: `go test ./...`
- Single test: `go test ./internal/store -run TestHybridSearch -v`
- Benchmarks (`docs/benchmarks.md` has the baseline): `go test ./internal/store -run '^$' -bench . -benchmem` (synthetic corpus, no db or model); `internal/embed` too with `HF_HOME` set (skipped otherwise). The **token report** — what each MCP tool's answer costs an agent, counted with an offline `o200k_base` tokenizer (a test-only dependency, kept out of the binary) — runs on the real corpus: `T7KB_BENCH_DB=<t7kb.db> HF_HOME=<models> TA_TOOLS_PATH=<bo3 root> go test ./internal/cli -run TestTokenReport -v`. Rerun it, and update `docs/benchmarks.md`, when you change a tool's output format. **Retrieval quality**: `TestRetrievalQuality` (same env) scores search on two judged sets in `internal/cli/testdata/` — `retrieval_eval.json` (tuning) and `retrieval_holdout.json` (held-out, judged blind) — with key@5, recall@10, MRR, nDCG@10. Run it before and after any ranking change and keep both sets' numbers in `docs/retrieval-quality.md`: a change must not lose on the held-out set, whatever it gains on tuning.

Any hybrid search (and `TestHybridSearch`) loads the embedding model via go-sentex. By default the model is looked up in a `models/` dir **beside the binary** (the release bundle); for dev, set `HF_HOME` to your global HuggingFace cache or it downloads ~87 MB on first use. `search --bm25` skips the embedder.

Run surfaces:
- `t7kb mcp` — stdio MCP server (primary; exposes `search`, `get`, `build`, `create`, `gdt_*` and `zone_*`)
- `t7kb search "<query>"` / `t7kb get <doc_id>` — one-shot CLI (`--scores` shows RRF + reliability)
- `t7kb` (no args) — interactive browse: query → numbered hits → type a number to read one
- `--version` reports the build version (injected via ldflags; "dev" locally)
- `t7kb update-check` — on-demand GitHub release check (`internal/cli/update.go`); never runs automatically, never downloads. Compares the ldflags version to `/releases/latest`'s tag by plain string equality, and lists each t7kb plugin install (from `claude plugin list --json`, per scope) whose version differs, with its update commands (`internal/cli/plugin_check.go`; silent without Claude Code). Never parse Claude Code's internal `installed_plugins.json` instead. Used by the `setup` skill's idempotency check, step 1.
- `t7kb build <name>` (`internal/cli/build.go`) — headlessly drives the **BO3 mod-tools** build pipeline (gdtdb → cod2map64 → radiant_modtools light → linker_modtools, optional game run) and prints a compact per-stage summary (`--json` for structured). One of the three **side-effecting** entry points (with `gdt edit --write` and `create --write`): it shells out to the Windows mod tools (Windows-only; needs the install), unlike the otherwise read-only/offline tool. Exposed both as the CLI subcommand and the `build` MCP tool (`buildToolDef` in `internal/cli/build_mcp.go`) — keep both behaviourally identical. Tools path resolves `--tools-path` > `$TA_TOOLS_PATH`. Non-obvious behaviour: cod2map runs with **cwd=`bin/`** (else it can't load `default_navmesh_settings.json` and silently skips navmesh); args go through `exec`, not a shell (git-bash/MSYS mangles `/update` and `+medium` and mis-reports native exit codes); the **detached** `radiant_modtools -ledSilent` light bake is waited on by **polling for its `.led`** output, not an exit code. The `run` stage starts `BlackOps3.exe` with the Launcher's own arguments and environment (`gameArgs`/`gameEnv` in `build.go` say which and why) and reports a failure if the game exits within 8 s. The `t7kb:compiling` skill routes agents `t7kb:build` (MCP) → `t7kb build` (CLI) → raw mod-tools binaries; if you change the tool surface, update that skill in the same commit. Keep it a thin orchestrator — build logic belongs to the mod tools.
- `t7kb create <name>` (`internal/scaffold`, `internal/cli/create_*.go`) — MCP `create`: the Launcher's File > New, with a dry run by default, no overwrite, and a template's stock assetlists merged rather than copied (the rules are in the package doc). Side-effecting.
- `t7kb gdt find|get|schema|edit|check|refs` (`internal/gdt`, wired in `internal/cli/gdt_ops.go` / `gdt_mcp.go` / `gdt_cmd.go`) — GDT authoring, exposed identically as the MCP tools `gdt_find`, `gdt_get`, `gdt_schema`, `gdt_edit`, `gdt_check`, `gdt_refs`. **Read the package doc, `internal/gdt/doc.go`, before changing any of them**: where the schema comes from, the index and its caches, what `gdt_edit` refuses and how it writes (surgical, verified, atomic), what `gdt_check` and `gdt_refs` cover, and the one rule for what counts as an error (anything stock GDTs do while still linking is not).
- `t7kb zone explain|contents|check|predict` (`internal/zone`, `internal/cli/zone_*.go`) — MCP `zone_explain`, `zone_contents`, `zone_check`, `zone_predict`. The first two read the report the linker writes on every link (`usermaps/<map>/zone_source/all/assetinfo/<map>.csv`: each packed asset, its bytes, its `parentStack` up to the zone line) and flag it stale when a file in `<map>.deps` or a non-stock GDT defining a packed asset changed since. `zone_check` resolves the map's `>class` chain (`share/zone_source/*.class`; `.zpkg` from the map's `zone_source/` first) to its `ignore` lists, whose active entries the linker packs only as a reference to the shipped asset (`ignore_missing_shipped` lists pack in full); `TestInheritMatchesLinker` (opt-in) checks the chain against the one atop each `.deps`. `zone_predict` needs no link: it runs the zone through `internal/deps` (`deps.OpenZone`) on request, for what the next link will pull in, referenced assets no GDT, file or stock list defines, and the GDT versions stock replaces — no sizes, ~15 s for a large map cold.
- DB resolution (`resolveDB`): `--db` > `$T7KB_DB` > beside the binary > `./t7kb.db`. It returns the intended path even if the file is absent — `ensureDB` (`internal/cli/db.go`) then unpacks a sibling `t7kb.db.zip` there on first run.

## Architecture

**Two-repo split (read this first).** The corpus and the DB build live upstream in the sibling `t7_knowledge` repo; the chain is `sources → build_kb.py → kb.db → make_t7kb.py → t7kb.db`. Do **not** add corpus ingestion or batch-embedding logic here. The ~3.5 GB `t7kb.db` exceeds GitHub's 2 GiB asset limit, so it ships **compressed as a separate `t7kb.db.zip` release asset** (the OS archives don't contain it); the binary auto-unpacks it beside itself on first run (`ensureDB`).

**The embedding-parity invariant (the #1 gotcha).** Vector search only works if the query is embedded with the **same model** that produced the stored chunk vectors. Both sides use **all-MiniLM-L6-v2 (384-d, L2-normalized)** — the corpus via Python fastembed upstream, the query via **go-sentex** here (identical vectors). If you change the model here you MUST rebuild the corpus upstream (`corpus.py` `EMBEDDING_MODEL` / `EMBEDDING_DIM`). `store.vectorRank` silently **skips** chunks whose dimension ≠ the query's, so a model/dim mismatch degrades to BM25-only with no error. The corpus is also chunked for MiniLM's ~256-token window, so the model choice is load-bearing on both chunking and vectors.

**Pure-Go, no cgo — a hard constraint.** It is what makes the single static binary and clean cross-compile work (no C compiler on the build host). SQLite is `modernc.org/sqlite` (not mattn); embeddings are `go-sentex`/gomlx (not onnxruntime). Don't introduce cgo deps. (The corpus is embedded in Python upstream because the pure-Go gomlx backend, ~3 chunks/s, is fine for one query but far too slow for ~380k chunks.)

**Retrieval pipeline.** `internal/store` owns it: `bm25Rank` (FTS5 `bm25()`), `vectorRank` (streams the `embeddings` table, or in the MCP server an in-memory copy, `vecindex.go`; cosine = dot since normalized; best chunk per doc), `rrfFuse` (k=60), `sortByFusedScore` (reliability tiebreak); BM25 weighs a title match 10× a body one (`titleWeight`). Ranking changes are judged on the tuning set and checked on the blind held-out set (see `TestRetrievalQuality` above); `docs/retrieval-quality.md` lists what was tried and rejected — read it before tuning ranking, and judge a fresh held-out set for the next decision (the current one has been used). `internal/embed` wraps go-sentex (one query embedding per search) and defaults `HF_HOME` to the beside-binary `models/`. `internal/cli` builds the cobra tree.

**Adding MCP tools (the server is built to grow).** Each feature is a *toolset* (`internal/cli/mcp.go`): its domain logic lives in its own `internal/<pkg>` (like `internal/gdt`), the operation both surfaces call in `internal/cli/<feature>_ops.go`, its MCP tool definitions in `<feature>_mcp.go` (a function returning a `toolset`, with an optional `warm` hook run at server start), and its cobra commands in `<feature>_cmd.go`. Register it with one line in `toolsets()`. A file format used by more than one domain, or a self-contained binary one, gets its own package under `internal/format/` (`xmodelbin`): it reads bytes and returns data, knows nothing of the install, and has a real-data oracle test; a format one domain uses stays in it (#21). Packages pass assets to each other as `asset.ID` (`internal/asset`: the linker's type and the name; key maps on `Key()`). What an asset pulls into a fastfile is `internal/deps`, the graph built on `gdt` and the formats (its package doc has the rules); `TestGraphMatchesLinker` (`T7KB_ORACLE=1`) scores it per edge family against a linked map's report (zm_test by default) — rerun it before and after changing an edge. MCP and CLI must behave identically, which is why both go through the `_ops.go` function; `TestToolsetsHaveUniqueDescribedToolsWithCLICommands` fails if a tool has no description, shares a name, or has no CLI command of the same name (`gdt_edit` ↔ `t7kb gdt edit`). Handlers answer through `jsonHandler`/`jsonResult` (`mcp_util.go`): compact JSON, no HTML escaping, errors returned as tool errors the agent can read. Decode structured arguments with `decodeArg`/`decodeStrict` so a misspelt key is an error. The server runs with `server.WithRecovery()` so a panicking handler can't kill the stdio session.

**MCP shape.** The `search` tool takes an optional `source` filter — groups (`api`, `scripts`, `docs`, `wiki`, `forums`, `discord`, `video`, `workspace`; `sourceGroups` in `internal/store/sources.go`, a group ending in `-` takes every source with that prefix) or exact names, applied inside both retrievers (BM25's SQL, and the vector scan by doc_id prefix — every doc_id is `<source>::…`); an unknown name is an error listing what exists. It returns ranked `doc_id` / `title` / `source` / `reliability` / snippet — deliberately NOT the RRF/vector internals (noise to an agent; reliability is the one ranking signal it gets). RRF scores are CLI-only. `get` serves the body a page at a time (`renderDoc`, `internal/cli/kb_doc.go`: 16,000 characters by default, `max_chars` up to 64,000, cut at a line break, ending with the `offset` for the next part; `find` starts the page at a phrase, ASCII-case-insensitively so byte offsets stay exact) because bodies reach 98 MB; the CLI `t7kb get` pages the same way (`--all` for the whole body), the interactive browse shows the whole body.

The DB schema (`documents`, `docs_fts`, `embeddings`) is in `docs/data-model.md`; per-row `source` + `url` carry attribution (`docs/NOTICE.md`).

## Releasing

Pushing a `v*` tag runs GoReleaser (`.github/goreleaser.yaml` + `.github/workflows/release.yml`): it cross-builds the binaries, runs a before-hook that downloads the embedding model into `models/`, and bundles binary + model + docs into per-platform archives. The version is injected via `-ldflags` into `internal/cli.version`.

- Release notes = curated `header` (tool blurb) + auto-generated `changelog` + curated `footer` (install steps), in that order. Edit `header`/`footer` in `.github/goreleaser.yaml` for the static parts. The changelog lists only what a user would notice — `feat` (✨ New), `fix` (🐛 Fixed) and `docs(skills)` (📚 Skill knowledge); `ci`/`chore`/`test`/`refactor`/other `docs` are dropped — and each line is the subject with its `type(scope):` prefix turned into a bold scope label, no SHA. So commit subjects *are* the release notes: write them for a modder reading the release page.
- **Optional highlights:** a hand-written `.github/release-notes/<tag>.md` committed before tagging goes on top of the generated changelog (which the release workflow then heads "All changes"). Without one, the release keeps the generated notes. Write it from `git log <prev-tag>..HEAD` bodies: lead with what the user can now do, no internals.
- `t7kb.db.zip` is **not** built by CI (it's built upstream). The release workflow **carries it forward** from the most recent earlier release that has one, and skips if the new release already has it — so only a *rebuilt* DB needs a manual upload: `gh release upload <tag> t7kb.db.zip --clobber`.
- Validate config changes with `goreleaser check --config .github/goreleaser.yaml`; dry-run with `goreleaser release --snapshot --clean --config .github/goreleaser.yaml`.
- **`plugin/.claude-plugin/plugin.json`'s `version` must match the tag before you push it.** `.github/workflows/release.yml` fails the job if they differ, so the Go release and the plugin version never drift — `t7kb update-check` relies on that to tell a user an "update available" also means a matching plugin/skills update. Bump the manifest version in the same commit/PR as the release-worthy change, before tagging. A local `pre-push` hook (see Conventions) catches the mismatch earlier; CI is the real enforcement.

## Conventions

- Conventional commits (`feat:`, `fix:`, `refactor:`, `chore:`, scopes like `feat(cli):`) — they drive the version bump intent even though the changelog body is curated.
- `*.db`, `*.db.zip`, and `models/` are build/ship artifacts — gitignored.
- Never hard-wrap markdown at 80 columns (or any fixed width). One line per paragraph / list item; let the editor soft-wrap.
- **Docs state rules, not their history.** Write the rule, the trap, and its why in one clause; how it was found, measured, calibrated or changed goes in the commit message or PR body, never in a markdown file (skills keep only a few-word provenance tag, per `t7kb:contribute`). A new detail goes where its reader is — the MCP tool description (agents), the skill (agents doing the craft), this file (contributors), `docs/` (reference) — and other files point to it rather than restate it. When an edit adds text, cut what it makes redundant.
- **Every markdown file has a word budget** by kind, enforced by `.github/scripts/check_markdown.py` (the `skills` workflow and the `pre-commit` hook run it; an over-budget file fails): README 750, this file 3,500, `templates/AGENTS.md` 1,200, a skill body 3,000, a skill reference 2,000, `docs/` 1,500, release highlights 300, anything else 1,000. It warns at 95% of a budget and on phrases that usually narrate history. **At the budget, never trim words elsewhere to make room** — that erodes a file at random (a fact dropped for being three words). Ask first where the new detail's reader is: if it isn't this file, put it there (a skill, the code, a package doc). If it is, move a whole block that has a better reader out of this file (here: a package's rules into `internal/<pkg>/doc.go`, as `internal/gdt/doc.go`; a skill's into `references/`); the checker's error lists the largest sections. A budget may be raised, but only deliberately: in a commit of its own that says why the content belongs in this file and what it costs its reader (tokens in every session for a file loaded into context), never to land another change.
- Run `git config core.hooksPath .github/hooks` once per clone to enable the local hooks (not automatic). `pre-commit` runs gofmt on the staged `.go` files and golangci-lint on just their packages (free for a commit with no Go; needs `golangci-lint` v2.14 on the PATH, else it skips the lint and says how to install it; it lints the working tree, not the index). `pre-push` checks the same `plugin.json`-version-matches-tag invariant as the release CI gate. Tests stay out of the hooks: a cold `TestHybridSearch` downloads the 87 MB model — CI runs them.
