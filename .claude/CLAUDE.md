# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`t7kb` is the shipped, **agent-first query tool** for a Black Ops 3 modding knowledge base: a single **pure-Go, no-cgo** binary that serves hybrid retrieval (FTS5 BM25 + vector cosine, fused with RRF) over a local SQLite index, `t7kb.db`. The primary surface is an **MCP server** for AI agents; it also has a small CLI. Everything runs locally and offline.

This repo is the **consumer**. It does NOT build `t7kb.db` — that is produced by the sibling **t7_knowledge** repo (see "Two-repo split").

## Repo layout

The repo is three things in one: the **Go tool**, a **Claude Code plugin**, and **install/docs**. Map of what lives where (so nothing reads as accidental duplication):

- `cmd/` + `internal/` — the Go tool (`t7kb`): CLI + MCP server. The only compiled artifact.
- `install/install.sh` + `install.ps1` — the **single source of truth for installation**. Everything else that mentions install just invokes these.
- `.claude-plugin/marketplace.json` — the **marketplace** catalog (what makes `/plugin marketplace add McReaper/t7_companion` work). Lists the plugin below.
- `plugin/.claude-plugin/plugin.json` — the **plugin** manifest itself. *Two different files on purpose:* marketplace = the catalog, plugin = the thing in it. Not a duplicate.
- `plugin/skills/*/SKILL.md` — the plugin's skills. `setup` is the **agent's** install action (it runs `install/install.sh` + `claude mcp add`) — i.e. the agent-facing mirror of the README's install, not a separate install method. Each skill's frontmatter `name` equals its directory name (the Agent Skills spec requires it, and Claude Code lists/invokes plugin skills as `t7kb:<directory>`), and skills refer to each other by that listed form, `t7kb:<name>`. `plugin/skills/contribute/scripts/check_skills.py` enforces this and the other format rules; `.github/workflows/skills.yml` runs it on every PR, and `plugin/evals/` holds the `claude plugin eval` trigger cases. `contribute` is the authoring guide for the skills themselves — and the path by which plugin users send a fix or a newly found trap upstream as a PR (when a new skill is warranted vs. extending one, the description/trigger craft, the claim-shaped-heading house style, the grounding order, and the follow-ups below) — **load it before writing or revising any `SKILL.md`**, and update it when a convention here changes. **Adding, renaming, or removing one has two required follow-ups, not one:** update `t7kb:knowledge-base`'s frontmatter `description` (it names every other domain skill by name to route around trigger overlap — the validator checks it) and `.claude-plugin/marketplace.json`'s plugin description. The README's own mermaid diagram deliberately does *not* enumerate skill names, specifically so it can't go stale the way it just did (fixed by de-listing rather than re-listing) — don't reintroduce a hardcoded skill list there.
- `templates/AGENTS.md` — the vendor-neutral primer a user drops at their **BO3 mod-tools root** (not per-map — ancestor-aware tools pick it up from any `usermaps/`/`mods/` subfolder underneath). `setup`'s step 3 offers to fetch it there, plus a `CLAUDE.md` that does `@AGENTS.md` for Claude Code.
- `README.md` — the lean **human-facing** front door: install + a one-line connect pointer + CLI.
- `docs/clients.md` — per-client MCP config (Codex/OpenCode/Cursor/Copilot/Claude) + the AGENTS.md editor table. The detail the README points at; lives only here.
- `.claude/CLAUDE.md` (this file) / `docs/NOTICE.md` / `docs/data-model.md` — contributor + licensing + schema docs.

Install is intentionally described for two audiences — the README (human) and the `setup` skill (agent) — but both call the same `install/` scripts, so there is one real source.

**Ground-truth discovery is closed-loop, not re-derived per session.** `t7kb:knowledge-base`'s "verify against ground truth" section tells the agent to check the raw mod-tools install; `setup` step 3 already has to walk up to that same root to place `AGENTS.md`/`CLAUDE.md` (see above), so it appends a "Raw mod-tools root: `<path>`" fact to the fetched `AGENTS.md` there. `t7kb:knowledge-base` checks that fact first before searching. If you touch either skill, keep this cross-reference intact — don't reintroduce a from-scratch search every session when `setup` already found the path once.

## Commands

Targets **Go 1.25** (`go.mod`). The machine's default `go` may be older; `GOTOOLCHAIN=auto` (the default) fetches the right toolchain on first build.

- Build: `go build -o t7kb.exe ./cmd/t7kb`
- Cross-compile (what CI ships): `CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./cmd/t7kb`
- Vet: `go vet ./...`
- Lint: `gofmt -l cmd internal` (must print nothing) and `golangci-lint run ./...` (v2.14; `.golangci.yml`). Beyond the standard set (staticcheck, errcheck, govet, …) it enforces limits set from the code's own shape (average cyclomatic complexity 6.6): cyclomatic ≤ 20, cognitive ≤ 30, a function ≤ 80 lines / 60 statements, a file ≤ 500 code lines, and nestif. Tests are exempt from the size/complexity limits. When a function trips one, split it by what it does (one check, one stage, one subcommand) rather than raising the limit or adding a `//nolint`.
- Test: `go test ./...`
- Single test: `go test ./internal/store -run TestHybridSearch -v`
- Benchmarks (`docs/benchmarks.md` has the baseline): `go test ./internal/store -run '^$' -bench . -benchmem` (synthetic corpus, no db or model); `internal/embed` too with `HF_HOME` set (skipped otherwise — in a test binary the model would download). The **token report** — what each MCP tool's answer costs an agent, counted with an offline `o200k_base` tokenizer, a test-only dependency kept out of the binary — runs on the real corpus: `T7KB_BENCH_DB=<t7kb.db> HF_HOME=<models> TA_TOOLS_PATH=<bo3 root> go test ./internal/cli -run TestTokenReport -v`. Rerun it, and update `docs/benchmarks.md`, when you change a tool's output format.

CI (`.github/workflows/ci.yml`) runs all of the above on every PR touching Go: gofmt, vet, golangci-lint, build, a cross-compile of both release targets with `CGO_ENABLED=0`, and the tests (the embedding model is cached between runs for `TestHybridSearch`). `skills.yml` validates the plugin skills separately.

Any hybrid search (and `TestHybridSearch`) loads the embedding model via go-sentex. By default the model is looked up in a `models/` dir **beside the binary** (the release bundle); for dev, set `HF_HOME` to your global HuggingFace cache or it downloads ~87 MB on first use. `search --bm25` skips the embedder.

Run surfaces:
- `t7kb mcp` — stdio MCP server (primary; exposes `search`, `get`, `build` and the `gdt_*` tools)
- `t7kb search "<query>"` / `t7kb get <doc_id>` — one-shot CLI (`--scores` shows RRF + reliability)
- `t7kb` (no args) — interactive browse: query → numbered hits → type a number to read one
- `--version` reports the build version (injected via ldflags; "dev" locally)
- `t7kb update-check` — on-demand-only GitHub release check (`internal/cli/update.go`); never runs automatically, never downloads anything itself. Compares the ldflags version against `/releases/latest`'s tag by plain string equality (no semver ordering needed — GitHub's "latest" is by definition newer than whatever's running). Wired into the `setup` skill's idempotency check, step 1.
- `t7kb build <name>` (`internal/cli/build.go`) — headlessly drives the **BO3 mod-tools** build pipeline (gdtdb → cod2map64 → radiant_modtools light → linker_modtools, optional game run) and prints a compact per-stage summary (`--json` for structured). It is one of the two **side-effecting subcommands** (with `gdt edit --write`): it shells out to the Windows mod tools (Windows-only; needs the install), unlike the otherwise read-only/offline/cross-platform tool. It exists so an agent can compile for the user cheaply (a parsed summary + first error, not each tool's hundreds of lines) — exposed **both ways**: the `t7kb build` CLI subcommand and the `build` MCP tool (`buildToolDef` in `internal/cli/build_mcp.go`), so it is one of the two write-capable tools on an otherwise read-only MCP surface (the other is `gdt_edit`) — keep both entry points behaviourally identical. Tools path resolves `--tools-path` > `$TA_TOOLS_PATH`. Three non-obvious things it bakes in (all found the hard way): cod2map runs with **cwd=`bin/`** (else it can't load `default_navmesh_settings.json` and silently skips navmesh), args go through `exec` not a shell (git-bash/MSYS otherwise mangles `/update` and `+medium` and mis-reports native exit codes), and the **detached** `radiant_modtools -ledSilent` light bake is waited on by **polling for its `.led`** output, not an exit code. The `run` stage starts `BlackOps3.exe` with the Launcher's own arguments, captured from the stock `modlauncher.exe`: `+set fs_game <map> +devmap <map>` for a usermap too (without `fs_game` it stays on the main menu), `+set fs_game <mod>` alone for a mod, optional dvars first (`--dvar`, or `--launcher-dvars` from `HKCU\Software\Treyarch\ModLauncher`). It sets `SteamAppId=311210`, without which a game started outside the Launcher shows "you must launch Steam" and exits, and it reports a failure if the game exits within 8 s. The `t7kb:compiling` skill routes agents `t7kb:build` (MCP) → `t7kb build` (CLI) → raw mod-tools binaries, in that order of preference; if you change the tool surface here, update that skill in the same commit — it drifted once already because the MCP tool shipped without it. Keep it a thin orchestrator — build logic belongs to the mod tools, not here.
- `t7kb gdt find|get|schema|edit|check|refs` (`internal/gdt`, wired in `internal/cli/gdt_ops.go` / `gdt_mcp.go` / `gdt_cmd.go`) — GDT authoring, exposed identically as the MCP tools `gdt_find`, `gdt_get`, `gdt_schema`, `gdt_edit`, `gdt_check`, `gdt_refs`. The schema comes from the install itself: `deffiles/<type>.awi` (the AngelScript that builds APE's property pages — `AddEntry_*` declarations are extracted statically, and a combo's options also when they're held in a variable built only from literals, heredocs and other such variables (`awivars.go`; anything assigned from a call, an index or a `+=` leaves the combo unchecked, and a `true` third argument makes it an editable combo whose list is only suggestions). The script isn't interpreted — of its 14 validation callbacks most only refresh labels; the ones that matter are ported: `ValidateLODs` as a gdt_check warning, `surfaceType` `<error>` (APE's default, an UNRECOVERABLE link error once the material reaches collision) as a warning, and the two that *write* fields on change — a `glossSurfaceType` preset writes `glossRangeMin/Max`, an image `semantic` sets `premulAlpha`/`streamable` — applied by `gdt_edit` (`apeeffects.go`) unless the request sets those fields itself) and, for materials, the techsetdef a `materialType` resolves to under `share/raw/techsetdefs_stable` (following `#include`s: texture slots with the GDT field and image semantic they read, the category `materialCategory` must equal, HLSL sources). There are no `.gdf` files — the `"type.gdf"` in a GDT names the `.awi`. Asset lookups go through an index of every GDT in the directories `gdtdb` scans (`bin/converter_gdt_dirs_0.txt`), cached on disk in the user cache dir (gob — JSON took ~270 ms of every CLI call to decode) and refreshed incrementally by mtime/size (the walk that finds new GDTs reads directories concurrently — `model_export` alone is ~270k files in ~38k directories, which took a sequential walk ~2.5 s of every CLI call); the MCP server warms it at startup, and a long session keeps it fresh (indexed files re-stat'd at most every 5 s on lookup, a background walk for new GDTs at most every 2 min) so GDTs saved in APE meanwhile are seen. Parsed GDTs are cached by mtime/size for read-only use (`Workspace.Load`) — never mutate what `Load` returns; edits parse their own copy. (`gdtdb/gdt.db` itself is SQLite but unreadable with a standard build — a table exceeds SQLite's default column limit.) `gdt_edit` is dry-run by default, refuses GDTs listed in `stock.gdtdef`, GDTs outside the directories gdtdb indexes (`Workspace.InGDTDirs` — a GDT anywhere else is never built), names/keys the format can't hold (`ValidName`), and a second asset of the same type and name. Writes are serialised per file (`Workspace.lockFile`), refused if the file changed on disk since it was read (an APE save in between), verified by re-parsing the output before anything is written (`File.Save`), and atomic with a `.bak`. When one GDT holds same-name assets of different types, an edit must say which (`type`), and lookups go by name *and* type or by file:line (`File.FindAll`/`AtLine`) — never the first match by name. The MCP server runs with `server.WithRecovery()` so a panicking handler can't kill the stdio session. It takes one asset or a batch (`assets`, applied in order in memory so later items see earlier ones, written once and only if no item has an error), and can create an image from a texture: the semantic from the techset slot it fills, every other field the most common value across stock images of that semantic (a single donor would drag in its quirks). `gdt_check` is the whole-GDT diagnostic pass — typed references (AssetCombo targets exist and have the right type; `$`-prefixed engine built-ins skipped), source files on disk (xmodel LODs under `model_export/`, xanim under `xanim_export/`, image `baseImage` under the root, other `Path` fields via the `.awi`'s `SetRelativePath`), parents, cross-GDT duplicates; it skips the "not declared in the .awi" warning for existing keys (APE writes script-built fields the static parse can't see). `gdt_refs` is the reverse lookup (field values and derived parents across all indexed GDTs; not `.xmodel_bin` material names). What `gdt_check` treats as an error was calibrated by running it over a whole install (3,006 GDTs, 260k assets) — `TestCalibrate` (`internal/gdt/calibrate_test.go`, opt-in via `T7KB_CALIBRATE`) reruns that and tallies issues by kind; diff its report before and after changing any rule: anything Treyarch's own stock GDTs do while still linking is not an error, which took errors from 207k to 1.3k. A hard rule found the same way: **a derived asset's parent must be in the same GDT** (all 16,972 in a stock install are; gdtdb otherwise fails with `Parent Entity '<name>' does not exist in GDT`), so `Resolved(f, a)` walks the chain inside one file, `gdt_edit` refuses a `parent` from another GDT, and deriving from a stock asset is impossible (`copy_from` it instead). The lessons, each a former false-positive class: **names are per type** — an image and a material called `clip` are fine (800+ such pairs in stock); only two definitions of the same resolved type are `Duplicate '<type>' asset` (`Workspace.FindTyped`/`Duplicates`; a derived asset takes its parent's type); a runtime-built field name is matched on **all** its literal parts (`"autogenLod" + i` vs `"autogenLod" + i + "Percent"`); a field declared again in another script branch with another kind or target is `Varies` and not type-checked (xanim's note `actionparam1`); APE matches field names and combo values case-insensitively (`"type"`/`"Type"`, `"stand"`/`Stand`), accepts `Label{value}` options by either part, the `.awi` default marker (`"<none>*"`), `True`/`False` checkboxes, and empty values as the default; `.awi` min/max are slider bounds (outside = warning); a combo value any stock GDT uses for that field is accepted even when the current `.awi` dropped it (its own `//legacy support` filter names, `<legacy>` gloss) — `stockUses`, scanned lazily once per type (~1.4 s for material; it keeps only combo fields — recording every field of every stock asset made it ~10 s); `AddEntry_Texture` is a source path, not an asset reference; a target-type mismatch is an error only for image/material/xmodel/xanim (elsewhere the `.awi` type is loose); a missing file is an error only for xmodel LODs, xanim exports and image textures (FX/surface-FX/collision paths ship compiled); and stale texture slots a techset doesn't read are skipped (stock keeps ~40k). Big results are capped for the agent: `gdt_check` details 25 assets and groups the rest by issue kind, `gdt_refs` lists 50. Writes are **surgical**: a parsed GDT keeps its source byte for byte and only the edited asset is re-rendered (hand-formatted and community GDTs are full of layout APE itself wouldn't write — reformatting the whole file would bury a one-field change in the git diff). Outputs are kept small on purpose, because they land in the agent's context: `gdt_get` hides empty, zero and default-valued fields unless `all`, and `gdt_schema` only lists names for a type over 80 fields unless filtered or given a `material_type` (a weapon schema is ~65k tokens in full). After a write, the build's default `gdtdb /update` indexes the change (verified); `build`'s `gdt_rebuild` runs `/rebuild` for the "every asset missing" recovery.
- DB resolution (`resolveDB`): `--db` > `$T7KB_DB` > beside the binary > `./t7kb.db`. It returns the intended path even if the file is absent — `ensureDB` (`internal/cli/db.go`) then unpacks a sibling `t7kb.db.zip` there on first run.

## Architecture

**Two-repo split (read this first).** The corpus and the DB build live upstream in the sibling `t7_knowledge` repo; the chain is `sources → build_kb.py → kb.db → make_t7kb.py → t7kb.db`. Do **not** add corpus ingestion or batch-embedding logic here — it belongs upstream. The ~3.5 GB `t7kb.db` exceeds GitHub's 2 GiB asset limit, so it ships **compressed as a separate `t7kb.db.zip` release asset** (the OS archives don't contain it); the binary auto-unpacks it beside itself on first run (see `ensureDB`).

**The embedding-parity invariant (the #1 gotcha).** Vector search only works if the query is embedded with the **same model** that produced the stored chunk vectors. Both sides use **all-MiniLM-L6-v2 (384-d, L2-normalized)** — the corpus via Python fastembed upstream, the query via **go-sentex** here — verified to produce identical vectors. If you change the model here you MUST rebuild the corpus upstream (`corpus.py` `EMBEDDING_MODEL` / `EMBEDDING_DIM`). Watch out: `store.vectorRank` silently **skips** chunks whose dimension ≠ the query's, so a model/dim mismatch degrades to BM25-only with no error. The corpus is also chunked for MiniLM's ~256-token window, so the model choice is load-bearing on both chunking and vectors.

**Pure-Go, no cgo — a hard constraint.** It is what makes the single static binary and clean cross-compile work (there is no C compiler on the build host). SQLite is `modernc.org/sqlite` (not mattn); embeddings are `go-sentex`/gomlx (not onnxruntime). Don't introduce cgo deps. (Aside: the corpus build embeds in Python because the pure-Go gomlx backend is ~3 chunks/s — fine for one query embed, far too slow for the ~350K-chunk corpus build.)

**Retrieval pipeline.** `internal/store` owns it: `bm25Rank` (FTS5 `bm25()`), `vectorRank` (streams the `embeddings` table; cosine = dot since normalized; best chunk per doc), `rrfFuse` (k=60), `sortByFusedScore` (reliability tiebreak). `internal/embed` wraps go-sentex (one query embedding per search) and defaults `HF_HOME` to the beside-binary `models/`. `internal/cli` builds the cobra tree.

**Adding MCP tools (the server is built to grow).** Each feature is a *toolset* (`internal/cli/mcp.go`): its domain logic lives in its own `internal/<pkg>` (like `internal/gdt`), the operation that both surfaces call in `internal/cli/<feature>_ops.go`, its MCP tool definitions in `<feature>_mcp.go` (a function returning a `toolset`, with an optional `warm` hook run at server start), and its cobra commands in `<feature>_cmd.go`. Register it with one line in `toolsets()`. MCP and CLI must behave identically, which is why both go through the `_ops.go` function; `TestToolsetsHaveUniqueDescribedToolsWithCLICommands` fails if a tool has no description, shares a name, or has no CLI command of the same name (`gdt_edit` ↔ `t7kb gdt edit`). Handlers answer through `jsonHandler`/`jsonResult` (`mcp_util.go`): compact JSON, no HTML escaping, and errors returned as tool errors the agent can read. Decode structured arguments with `decodeArg`/`decodeStrict` so a misspelt key is an error. The server runs with `server.WithRecovery()`.

**MCP shape.** The `search` tool returns ranked `doc_id` / `title` / `source` / `reliability` / snippet — deliberately NOT the RRF/vector internals (noise to an agent; reliability is the one ranking signal it gets). RRF scores are CLI-only. `get` serves the body a page at a time (`renderDoc`, `internal/cli/kb_doc.go`: 16,000 characters by default, `max_chars` up to 64,000, cut at a line break, ending with the `offset` for the next part; `find` starts the page at a phrase, ASCII-case-insensitively so byte offsets stay exact — on the bench queries it brings the snippet's passage into the one page returned for 7/7 paged hits, against 4/7 for the first page) — the corpus's p99 body is 275k characters and its largest 98 MB, so an uncapped `get` cost up to ~40k tokens; the CLI `t7kb get` pages the same way (`--all` for the whole body), the interactive browse shows the whole body.

The DB schema (`documents`, `docs_fts`, `embeddings`) is in `docs/data-model.md`; per-row `source` + `url` carry attribution (`docs/NOTICE.md`).

## Releasing

Pushing a `v*` tag runs GoReleaser (`.github/goreleaser.yaml` + `.github/workflows/release.yml`): it cross-builds the binaries, runs a before-hook that downloads the embedding model into `models/`, and bundles binary + model + docs into per-platform archives. The version is injected via `-ldflags` into `internal/cli.version`.

- Release notes = curated `header` (tool blurb) + auto-generated `changelog` + curated `footer` (install steps), in that order. Edit `header`/`footer` in `.github/goreleaser.yaml` for the static parts; the changelog itself needs no per-release edits. It only lists what a user would notice — `feat` (✨ New), `fix` (🐛 Fixed) and `docs(skills)` (📚 Skill knowledge, since skill content ships to plugin users); `ci`/`chore`/`test`/`refactor`/other `docs` match no group and are dropped — and each line is the subject with its `type(scope):` prefix turned into a bold scope label, no SHA. So commit subjects *are* the release notes: write them for a modder reading the release page.
- **Optional highlights:** a hand-written `.github/release-notes/<tag>.md` (e.g. `v2.1.0.md`) committed before tagging is put on top of the generated changelog by the release workflow (which then heads the generated part "All changes"). Without one, the release just keeps the generated notes — nothing breaks. For a release worth announcing, write it from the range's commit bodies (`git log <prev-tag>..HEAD`): lead with what the user can now do, plain language, no internals.
- `t7kb.db.zip` is **not** built by CI (it's large and built upstream). The release workflow **carries it forward** from the most recent earlier release that has one, and skips if the new release already has it — so only a *rebuilt* DB needs a manual upload: `gh release upload <tag> t7kb.db.zip --clobber`.
- Validate config changes with `goreleaser check --config .github/goreleaser.yaml`; dry-run with `goreleaser release --snapshot --clean --config .github/goreleaser.yaml`.
- **`plugin/.claude-plugin/plugin.json`'s `version` must match the tag before you push it.** `.github/workflows/release.yml` gates on this (fails the job if they differ) so the Go release and the Claude Code plugin version can never drift apart — `t7kb update-check` relies on that invariant to tell a user an "update available" also means a matching plugin/skills update exists. Bump the manifest version in the same commit/PR as the release-worthy change, before tagging. A local `pre-push` hook (see Conventions) catches the mismatch earlier, but CI is the real enforcement.

## Conventions

- Conventional commits (`feat:`, `fix:`, `refactor:`, `chore:`, scopes like `feat(cli):`) — they drive the version bump intent even though the changelog body is curated.
- `*.db`, `*.db.zip`, and `models/` are build/ship artifacts — gitignored.
- Never hard-wrap markdown at 80 columns (or any fixed width). One line per paragraph / list item; let the editor soft-wrap. The maintainer is allergic to fixed-width reflow.
- Run `git config core.hooksPath .github/hooks` once per clone to enable the local hooks. Not automatic — a fresh clone won't have them until you run this. `pre-commit` runs gofmt on the staged `.go` files and golangci-lint on just their packages (~2 s warm; free for a commit with no Go; needs `golangci-lint` v2.14 on the PATH, else it skips the lint and says how to install it; it lints the working tree, not the index). `pre-push` checks the same `plugin.json`-version-matches-tag invariant as the release CI gate, before you push a tag. Tests stay out of the hooks: a cold `TestHybridSearch` downloads the 87 MB model — CI runs them.
